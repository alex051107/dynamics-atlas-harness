# "该不该做 Rules Table"这个问题，9 月 8 日已经有答案了；现在要做的是把测试对齐到那个答案

2026-09-10 · 依据：你 9 月 8 日的《Dynamics Atlas：我们想解决什么，已经做到哪里》（`research_reset_review_20260908/outputs/REPORT_ZH.md`）、同日 Pro 的概念审查与战略审查（`pro_concept/reply.md`、`pro_strategy/reply.md`）、8 月 17 日 Pro 对 Rules Table 的审查（`external_reviews/20260817_…`）、以及 9 月 9–10 日之后实际发生的事。

## 1. 那几份分析对"形式"的结论，三句话

**Pro 9 月 8 日战略审查的判定：** "靠 Rules Table 辅助合理；靠扩充 Rules Table 承担主要科学推断，既没有方法学理由，也没有项目内效果证据。"它把 Rules Table 拆成三个问题分别回答：

| 问题 | 结论 |
|---|---|
| 作为可审阅载体（一张给专家看的表） | 适合。但表里该写的是"适用条件、科学理由、对应方法、结论边界"，不是规则编号加 PASS/FAIL |
| 作为推断或调度机制（引擎） | 有限菜单和重复处理上有用；但科学上最难的判断发生在规则触发之前，那部分是人工整理的功劳，要单独计入 |
| 作为整个研究的组织中心 | **不建议继续。** 规则覆盖和科学回答之间没有自动对应；"取消规则扩张对研究议程的支配" |

**它推荐的最低复杂度形式：** 明确的科学问题与分析协议 + 现成的数值方法（BME、IMP、Metainference 这类）+ 逐项说明证据支持什么的结果报告。Rules Table 作为方法前提和结论边界的可审阅说明；规则引擎和 Agent 都是待比较的可选执行方式，不是必须保留的核心。

**你 9 月 8 日报告的结论一致：** "当前值得保留的是有来源、能影响具体分析的规则；是否需要额外的通用引擎，是另一个尚未得到效果证据的问题。"并且明确写了"近期不默认启动五组、六个新来源组、60 份答复的大比较"，先交科学结果。

**8 月 17 日 Pro 的 Rules Table 审查早就说了同一件事：** "简化后继续"，Rules Table 保留为 source-linked candidate registry（有来源的候选规则账本），不当运行时判据。

## 2. Pro 给的"能结束争论的比较"长什么样

五个条件，同资料同工具同预算，分别估计四种贡献：

| 条件 | 内容 | 估计什么 |
|---|---|---|
| U | 原资料 + 工具，LLM 自己分析 | 朴素基线 |
| D | U + 整理好的资料（事实索引、字段与来源对应） | D−U：整理资料的贡献 |
| P | D + 一段明确的科学分析协议，LLM 动态选方法 | P−D：协议的贡献 |
| F | 与 P 同资料同协议，由预先写好的普通脚本执行 | P−F：动态选择值不值 |
| R | 与 F 同资料同协议同工具，由冻结的 Rules 选分析 | R−F：规则执行值不值 |

外加三条硬要求：不加"Rules + Agent"第六组；两个开发组加至少六个独立测试组（你的报告把它缩成"最多两个未用组、两条路径、四份答复"的投入判断）；停止条件写死：继续投 Rules 只有两条路，**质量路径**（在 ≥ 2 个独立组纠正了实质科学错误且没有损失）或**效率路径**（回答不劣于固定流程且人工时间省 ≥ 25%）；结果不清楚就"暂不继续为它支付中心架构的成本"。

## 4. 所以到底该怎么做（判断）

**形式问题不用再讨论，三份分析已经收敛：** 科学问题和协议是中心，成熟方法算数，Rules Table 留作可审阅的前提与边界说明，引擎和 Agent 是要证明自己的可选执行方式。现在的科学交付（HSP90、DHFR）已经是这个形式；Rules 被暂停扩展也符合。**没有跑偏的是科学，跑偏的是测试设计。**

**要测"你做了那么久的 Rules Table 有没有用"，最锋利也最便宜的问题是 R 减 P：** 33 条注册表加选择器选出来的规则提示，比一段人手写的 7 条协议（9 月 9 日已经有的 `ACTIVE_RULES_ZH.md`）多带来了什么。如果 R 和 P 一样，表的价值就是"文献知识库 + 检查清单"，选择器不值得维护；如果 R 比 P 好，才值得继续建。这一比一步就能做，因为 P 组的文本早就存在。

**改动只有三处：** 把第二、三轮的三组改成 D（整理资料）/ P（加七条协议）/ R（加注册表选出的规则），去掉 C；F 不用单独跑，三轮确定性脚本的结果就是评分依据和"必须击败的基线"；判定改用 Pro 的两条路（质量、效率），并把人工时间记进成本。独立测试组只有 ADK 一个，所以结论是投入决定不是正确率，这和你 9 月 8 日报告的口径一致。

**Rules Table 本身要改的方向也已经定了：** 表的内容改成"适用条件、科学理由、对应方法、结论边界"（Track C 的渲染修复是第一步），不再按"还缺几条规则"衡量进度。

## 5. 一句话
Rules Table 该做，但只做成一张专家能审的前提与边界表；它值不值得配一个选择器和引擎，用 R 减 P 这一步测出来；科学交付按"问题 + 协议 + 成熟方法 + 逐项报告"继续，不等测试结果。
