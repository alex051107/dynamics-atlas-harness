# 教训账本（K-Ras 开发案例，2026-09-25 至 09-26）

给 Codex 通用流程与下一个案例用。每条写现象、后果、通用做法、来源。只收在真实数据或真实运行里发生过的事；推测不收。

## 一、正控与数据里的陷阱

**1. 存档参数文件里就是答案。**
- 现象：作者存档的 ChemEx 参数目录写着全局 kex、pB 和逐残基 Δϖ；实验配置的残基列表后面还带着作者的分类注释（"SlowEx : dR2 ~ …"）。
- 后果：原样放进解题工作区等于直接把答案给了 Agent。
- 通用做法：构建工作区时逐文件判定"实测 / 作者拟合结果 / 注释"，只保留实测；剥离清单写进泄露审计，审计文件放在工作区外。
- 来源：`blind_workspace_v1_LEAK_AUDIT.json`、`kras_ws_v3_LEAK_AUDIT.json`、`draft_notes.md`。

**2. 作者参数文件里的符号不是最终符号。**
- 现象：WT 参数文件头注明"CPMG global best fit"，其中 V29、Y40、Q70 的 Δϖ 符号与原始 CEST 次级凹陷的位置相反。
- 后果：若拿它当参照答案或初值，会得出错误的符号。
- 通用做法：只用 CPMG 得到的 Δϖ 视为无符号；符号只采信 CEST（或经校准的 HSQC/HMQC）。
- 来源：`draft_notes.md` "Positive controls"。

**3. 联合拟合对符号初值敏感。**
- 现象：CPMG+CEST 联合拟合如果全部从正号起步，WT 会落到 kex 460–680 s⁻¹ 的局部极小；逐残基扫描符号后恢复到约 400 s⁻¹。|Δϖ| 在 15–17 ppm 的残基从小初值起步也会卡住，参数边界 ±15 ppm 同样不够。
- 后果：数值偏离，还可能被误读成"过程异质"。V3 有两条运行的首轮逐残基拟合因此看起来速率分散，事后都查明是符号初值造成的。
- 通用做法：联合拟合前先对每个残基做多起点、双符号的 CEST 扫描；参数边界要覆盖参照态之间的最大位移差。
- 来源：`draft_notes.md`；`runs/V3_N2_r*/REPORT.md`、`runs/V3_C2_r2/REPORT.md`。

**4. 条件不同的公开参照：有的能用，有的是陷阱。**
- 现象：WT·GDP 的 BMRB 27720（pH 7.4、含盐）与作者同缓冲液的 GDP 位移中位差只有 0.046 ppm，可直接用；同条件的 GTP 条目 BMRB 28021 与本研究 GTP 位移的中位绝对偏差 3.75 ppm、最大 27 ppm，拿它做条件校正会把 Switch I 对 GDP 的 R² 从 0.97 毁到 0.38。
- 后果：把"做校正"当成默认的严谨动作，反而会引入错误。
- 通用做法：用于校正的条目必须先在"应当一致的残基"上与本数据核对；偏差大到不像同一个状态时就不用。
- 来源：`draft_notes.md`；第一轮报告 §4。

**5. 公开数据格式不统一。**
- 现象：同一存档里 G12D 的文件用三字母残基名（ASP012N），G12C 的配置用新版 ChemEx 格式（profiles 是表而不是列表）；GDP 对照的 Y32、Y64 在基态位移表里缺失。
- 后果：解析错一次，残基与位移就会错配；缺失若被静默跳过，会被读成"没有信号"。
- 通用做法：构建完工作区后，把每个残基标签与构建体序列逐一核对；工具返回输入数、分析数和逐条跳过原因。
- 来源：`draft_notes.md`；`resumption_20260926/independent_audit/REVIEW_ZH.md`。

**6. 手写引擎相对标准软件的偏差尚未量化。**
- 现象：正控里本引擎给出 kex 380 ± 8 s⁻¹，论文（ChemEx）为 400 ± 12 s⁻¹；本引擎假设理想脉冲、忽略 B1 不均匀性、次要态 R2 等于主态。
- 后果：所有"恢复了 Table 1"的判断都建立在一个没有外部交叉验证的引擎上。
- 通用做法：能用领域标准软件就用；自写的计算层至少与标准软件交叉验证一次，偏差写进结论边界。
- 结果（2026-09-26）：ChemEx 用作者配置复现 Table 1（394 s⁻¹、10.17%）；本地引擎同条件下 kex 系统偏低约 4%、|Δϖ| 偏高约 3%，符号与相对大小一致（r 0.9996）。ChemEx 同一拟合约需 4 小时，本地引擎数秒——Agent 工具保留本地引擎，正式数值用 ChemEx 复算。
- 来源：第一轮报告 §4；`FABLE_DEVIATION_REVIEW_ZH.md` D3；`engine_xval/CHEMEX_VS_LOCAL_WT.md`。

## 二、泄露的类别

1. 作者拟合参数文件与配置注释（见一.1）。
2. 数据库条目的标题和引文：BMRB 52021/52023/52024 的引文标题就是目标论文标题。工具返回时剥掉标题与引文，并屏蔽目标条目；屏蔽前要规范化编号，否则可以用非规范写法绕过。
3. 工具与参照库的命名：参照集叫"random_coil_potenci"、"GDP_bound_same_conditions"，本身就在提示候选参照。这种提示无法完全消除，但要在报告里写明"哪些选项是框架给的"。
4. 题面用词：题面把 GDP 样品叫"对照样品"，并写明"每 3 天换样是因为 GTP 缓慢水解"，等于提示了"要检查水解伪影、找一个过程不存在的对照"。保留科学必需的样品信息时，要在报告里注明这些是题目给定、不是 Agent 自己想到的。
5. 工作区外文件的可达性：参照工具曾能读回工作区外的无害探测文件（已修）；沙箱 Python 需要拒绝读取整个用户目录，只放行工作区和临时目录。
6. 模型先验：Agent 叫出 "state 1"、用 T35S 检索 state 1 参照，靠的都是预训练知识。这类路线对没有文献先验的蛋白不可复制，报告要标为"外部知识驱动"。

## 三、评测的教训

1. 判据写成"是否命中论文的读法"，会把工作引向对标签的优化；而且论文读法本身会被概括错（判据 c 把 Switch II 写成"有序但不同于 GDP"，论文两项指标其实都更支持 GDP）。评分应分两列：是否恢复论文结论、结论在现有数据下是否站得住。
2. 覆盖要从数据清单出发。WT T35（全数据集最大的 |Δϖ|）在 6 条真实运行里有 4 条根本没进拟合；只检查"已拟合残基里最大的五个"查不出来。评分对象应是 `actions.jsonl` 与 `fits/`，报告文字是次要证据。
3. 区域结论不能从整体平均推出。多数运行把 Switch I、II 和 P-loop 合在一起算 R²；比较工具改成一次给出每个区域、每类参照的结果后，逐区比较才普遍出现。
4. 每组 3 条只能做开发诊断：1/3 → 2/3 的变化不构成机制结论。
5. 负对照要内部自洽：合成的次要态替换了 ¹⁵N 数据，却留下真实的 HSQC/HMQC 符号文件。主终点只看被替换的样品。Agent 能识破"过于完美"的合成数据（6/6 标为异常），这本身说明负对照需要做得更像真数据。
6. 行为检查有效且便宜：删除符号证据后 Agent 收窄结构结论；改编号后结论不变。

## 四、工程的教训

1. 桌面目录被 iCloud 同步，重建工作区时生成冲突副本（"G12C 2"、"references 2.py"）。运行目录和工作树都应放在非同步位置，构建器要拒绝意外条目。
2. 三个运行并行时，数值库默认线程互相抢核，一次联合拟合拖到几分钟。每个工具进程限制线程数；批量线性代数替代逐条矩阵指数（结果一致到 10⁻¹³ 量级）。
3. 每轮改写历史消息会让提示缓存失效、成本上升；超过阈值时一次性批量裁剪，裁剪处保留观察编号以便回读。
4. 模型版本与客户端版本要对上：Opus 5.5 需要 Claude Code ≥ 2.1.280；PATH 上的旧版本会在第一次调用就失败。
5. 并行调用与反思闸门冲突：检查点之后并行发出的分析调用被闸门成批拦下，属于纯开销；给工具调用加顺序锁后解决。
6. 两个会话改同一份源码，冻结指纹会在运行之间漂移；需要按时间戳核对"哪条运行用了哪个版本"，并约定写入边界。

## 五、做对了、值得保留的做法

- 解题会话隔离：无内置工具、无设置来源、严格 MCP、中性工作目录、沙箱只读；启动前用探针核对上下文。
- 每次分析调用写明目的与预期；观察按编号存档、可分页回读；研究状态由框架持有，含撤回记录。
- 先正控、后盲测；行为检查与负对照；预登记（判据要按上面第三节改）。
- 用选择性证据拆分解释：CEST 定符号、GDP 对照排除污染、配体距离区分局部化学与构象。
